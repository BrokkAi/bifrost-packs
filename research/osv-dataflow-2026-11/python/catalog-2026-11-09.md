blocked, first on CPython version evidence (bifrost-dev#3867), and one (#359)

## Why most leads are blocked

Every lead's theoretical policy applies "only to the affected OSV ranges".
Bifrost 0.15.1 still publishes no CPython interpreter or Python dependency
evidence to policies (bifrost-dev#3867; the 0.15.1 reproduction is in the
earlier round's `probe/version-evidence`), and a taint policy could not join
such evidence to a sink anyway (bifrost-dev#10005). So the affected-version
part of every lead is blocked.

A lead ships only when it has a **version-independent part**: a flow that is a
hazard on every CPython version, so reporting it without version evidence is
truthful. That is the precedent of #270 and #272. Only #355 has one that the
engine proves today. For the others the fix itself removes the hazard (a
regression, a missing check, a parser bug or classification data), so a
version-free rule would report fixed interpreters, which the leads forbid.

## Shipped rule (#355)

`bifrost.security.python.process-input-to-venv-create` reports an
`os.environ` or `sys.argv` keyed read that reaches `env_dir` of `venv.create`.
On every interpreter that input chooses where an interpreter and activation
scripts are written and which directory `clear=True` empties; on affected
interpreters it also becomes shell code in `bin/activate`. The sources are
those of `process-input-to-os-system`. The rule uses `require-model` and is
opt-in. Its fixture is `proven_by_summary` with four definite findings; the
near misses (constant directory, unused input, a local `venv` lookalike) are
clean and `EnvBuilder(...).create(...)` and an unresolved helper stay
inconclusive. See
[`fixtures/policy/bifrost.security/python-process-input-to-venv-create`](../../../fixtures/policy/bifrost.security/python-process-input-to-venv-create/README.md).

Model changes:

- `bifrost.python-stdlib-api-declarations` 0.6.0 → **0.7.0** adds the `venv`
  module and `create(env_dir, system_site_packages, clear, symlinks, with_pip,
  prompt, upgrade_deps, *, scm_ignore_files)` from the pinned typeshed
  `venv/__init__.pyi`, with `callable_family_complete`.
- `bifrost.python-security-sink-summaries` 0.5.0 → **0.6.0** adds a complete
  summary: an `escape` of `env_dir` and of `prompt`, no transfers.
- `bifrost.security` 2.3.0 (released in rules 0.11.0) → **2.4.0**.

Release recipes are not changed.

### Engine findings from #355

`probe/355-venv` holds the call shapes. `venv.create(sys.argv[1])`,
`venv.create(sys.argv[1], False, True)` and `venv.create(env_dir=...)` are
`proven_by_summary`. `venv.create(sys.argv[1], with_pip=True)` fails the run
with `internal_invariant` ("external summary aliases require one synthetic
unmaterialized call shape"). This is bifrost-dev#9991, closed upstream on
2026-11-07 but not in a release. The new data point, added to that issue, is
that a `named_only` formal is not needed: a keyword that skips any defaulted
positional formal fails. `venv.create(".venv", prompt="build")`, with no
source, completes.

A lookalike that builds a local object before reading `sys.argv` turned the
whole fixture inconclusive and dropped every `sys.argv` finding, not only that
procedure's. That is bifrost-dev#9999; the fixture reads the input first.

## Per-lead notes

- **#348, #349 (typestate).** Typestate has an `after-exceptional-return`
  call phase, so "a `decompress()` that raised, then another `decompress()` on
  the same object" is expressible (`probe/348-bz2-typestate`, with a research
  `bz2` model). It never runs: the subject is the return value of
  `bz2.BZ2Decompressor()`, and a Python constructor call to a model-declared
  `__init__` leaves `call_bindings` at `dispatch outcome=unproven,
  coverage=open`. All four cases (reuse, fresh object in the handler, no
  `try`, re-raise) are `inconclusive (partial_discovery)` with no automaton
  result. The control `ftp-control` shows the same with the shipped, reviewed
  `ftplib.FTP.__init__` model (copy `bifrost.python-stdlib-api-declarations`
  into `.bifrost/semantic-models` to run it). An exact locator
  (`"bz2.BZ2Decompressor.__init__" :proof exact`) behaves the same. Filed as
  bifrost-dev#11329. The same gap blocks premium #602 (Pillow).
- **#353:** Same shape as #273: `poplib.POP3(host)` is built before the user
  name is read, so the source is lost (bifrost-dev#9999), and the fixed runtime
  rejects control characters, so there is no version-free part.
- **#356:** The Go analogue shipped (#252), so this is the most promising
  next lead. It needs reviewed `urllib.request.urlopen` return-class and
  `http.client.HTTPResponse.read` models, then a re-probe of the `.read()` call
  that the earlier round found inconclusive (`probe/270-urlopen/v-read`).
- **#347:** Assigning `SSLSocket.context` is documented and safe; the defect
  needs "the original context has no other strong reference while a native
  callback can still run". No Bifrost policy family reasons about object
  lifetime. No engine issue was filed, because the lead is version-gated first
  and this is a new analysis family, not a defect.
- **#359:** Decoding process input with `urlsafe_b64decode` is ordinary. The
  lead's limitation says ordinary users are unaffected, so a flow-only rule
  would be noise. It needs evidence that the application treats a successful
  decode as alphabet validation.
